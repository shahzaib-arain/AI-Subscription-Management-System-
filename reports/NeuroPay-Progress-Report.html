01 — Executive summary

One layer is real. The layer the FYP is graded on isn't built yet.

The repository currently contains a fully designed React Native (Expo) mobile shell and a Spring Boot authentication service — both genuinely solid. What it does not yet contain is any part of the system the proposal's four research objectives actually promise: a subscription data model, a transaction pipeline, an AI detection engine, or fraud/anomaly logic. Every subscription, alert, and "AI insight" visible in the app today is a hard-coded array in frontend/constants/mockData.ts, not a live signal from the backend.

The proposal is dated 12 March 2026; today is roughly week 24 of the stated 43-week plan (approximate, read off the submitted chart). By this point, Phase 2 (weeks 13–22) commits the team to a working Transaction & Subscription Service, an Initial Subscription Detection Model, and a Fraud Detection Algorithm Prototype — none of which exist in the repo. What has been delivered ahead of schedule is Security & Authentication Modules, formally a Phase 3 (week ~28) item, plus a level of frontend dashboard polish beyond what Phase 2 asked for. In short: the team has been building the shell and the login system very well, while the graded core — subscription intelligence — hasn't started. That's the single most important finding in this report.

The rest of this document breaks that gap down feature-by-feature, separates what's genuinely done from what only looks done in the UI, and lays out a feasibility-checked path — including several commercially interesting additions (a subscription marketplace, plan comparison, AI cost recommendations) — to bring the build back in line with the proposal before final submission.

03 — What's actually completed

Solid, production-shaped work — mostly in one layer

This is real, working code, not a mockup. It's just concentrated in identity/auth and the visual shell rather than the subscription domain.

Backend — authentication service

  • Full JWT sign-up / sign-in with BCrypt password hashing, access + refresh tokens (JwtService, JwtAuthFilter, SecurityConfig)
  • Forgot-password / reset-password flow with a real expiring-token entity (PasswordResetToken, PasswordResetTokenRepository) rather than a stubbed endpoint
  • Transactional HTML email via Gmail SMTP + Thymeleaf templates for welcome and reset-password mail (MailService.java, MailConfig.java), sent asynchronously
  • Consistent API envelope (ApiResponse<T>) and a global exception handler covering duplicate-user, invalid-token, and not-found cases
  • Role enum and Spring Security wiring in place for future authorization checks

Frontend — application shell

  • Complete Expo Router navigation: auth stack (login, signup, forgot/reset password, add-card) + 5-tab shell (home, subscriptions, wallet, alerts, profile) + a cards stack
  • Auth context wired live to the backend (services/api.ts, context/AuthContext.tsx) — sign-up/sign-in genuinely round-trip to Spring Boot and store the JWT
  • A polished, consistent dark-mode design system (Manrope type scale, motion via Reanimated) applied across every screen
  • A believable virtual-card visualization component (components/ui/CreditCard.tsx) reflecting the real backend-issued card number
04 — Partially completed

Looks finished on screen; the other half is missing

These are the highest-leverage fixes: the UI work is already paid for, so closing each gap is mostly backend and wiring, not redesign.

  • Wallet balance
    Deposit/freeze UI is complete and feels real, but the balance is a browser-only localStorage number with no server-side wallet entity or transaction ledger. On native Android/iOS it silently doesn't persist at all — safeStorage is a web-only no-op.
    Needs backend
  • Virtual card issuance
    VirtualCardService guarantees a unique-looking number, but it isn't attached to a real card network, has no spend limit enforcement, and can't actually authorize a charge.
    Cosmetic
  • External funding cards
    Add/edit/delete all work against in-memory component state seeded with two demo cards; nothing survives a reload, and there's no encryption/tokenization story for card data at all.
    UI only
  • Notifications
    The email pipe is real and reusable — it just isn't hooked to anything except auth. There's no notification table, no in-app inbox backing the Alerts tab, and no SMS/push transport.
    Auth-only
  • Profile screen
    profile.tsx doesn't call useAuth() at all — name, email, and the "$247/mo · $540 saved" stats are hard-coded, so it currently shows the same fake profile for every logged-in user.
    Not wired
05 — Proposed but not started

The core of the FYP is currently a blank slate

These are the objectives the proposal is actually graded against. None have any code, schema, or scaffolding yet.

  • AI microservice — the proposal's own architecture calls for a Python/scikit-learn/TensorFlow service; zero Python files exist in the repository.
  • Subscription & Transaction data model — no entities, repositories, or migrations for subscriptions, transactions, or merchants. There is nothing yet for an AI model to detect patterns from.
  • Recurring-payment / subscription detection logic — rule-based or ML — does not exist.
  • Fraud / anomaly scoring with confidence output — does not exist.
  • Inactive-subscription usage tracking — no usage signal is ever captured, so "unused for 45 days" can't be computed.
  • Subscription lifecycle endpoints — approve, pause, block, cancel — none are exposed by the backend.
  • Notification service as its own component — the architecture diagram calls for one; today it's two email templates bolted onto auth.
  • Automated tests — beyond the default Spring Boot scaffold test (NeuroPayApplicationTests), there is no test coverage on either side of the stack.

B. AI & intelligence

The part the grade actually hinges on
  • Rule-based recurring-payment detector (v1)
    Group transactions by merchant + amount tolerance + interval (7/30/365 days) before reaching for ML — a believable, gradeable "detection" step that also produces labelled data for a later model.
    Possible now
  • ML anomaly / fraud scoring
    Isolation Forest or a small autoencoder over transaction features, trained on synthetic/sandbox data, producing the confidence score the proposal promises.
    Possible now, on synthetic data
  • Merchant name normalization & auto-categorization
    Turn "NFLX*8817262" into "Netflix / Entertainment" via a small NER model or an LLM call, then group spend by category.
    Possible now
  • Personalized savings recommendations
    "You haven't opened Figma in 45 days — pausing saves $180/yr" generated from real usage/billing data rather than typed as a string.
    Possible now
  • Bank-grade fraud accuracy at the 95%+ figure quoted in the pitch deck
    Requires volumes of real labelled transaction data no student project has access to.
    Significant R&D — treat as a stretch target, report honestly against synthetic-data accuracy

C. Payments & banking

  • Real wallet ledger

  • A real bank's fraud webhook / core-banking integration
    What "banking platform" integration would mean in production.

    11 — Risks & housekeeping

    Fix these regardless of feature priority

    ⚠
    Secrets are committed in plaintext

    application.yml contains a live-looking Postgres password, a Gmail app password, and the JWT signing key, all checked into the repository. Rotate these credentials and move them to environment variables before the repo is ever shared publicly or with markers outside the team.

    📱
    Wallet balance doesn't survive a real mobile install

    safeStorage in AuthContext.tsx only reads/writes on Platform.OS === "web". On an actual Android/iOS build, deposits silently vanish on next launch — worth fixing before a live demo on a phone, not just in the browser preview.

    👤
    Profile screen shows fake data to every user

    profile.tsx hard-codes a name, email, and spend stats instead of reading useAuth() — a quick, high-visibility fix.

    🏦
    Calibrate the "banking integration" claim

    The pitch deck's "direct banking integration" and "Pakistan Focus... local banking APIs" language over-promises relative to what's achievable without an actual bank partner. Recommend reframing the final report around a self-issued virtual card + simulated bank feed, which is exactly what's buildable, rather than implying live third-party bank connectivity.

    12 — Final recommendations

    The five moves that matter most before submission

    1. Build the data model first, not the model
      A Subscription/Transaction schema and a synthetic feed unlock everything else — detection, alerts, and analytics all read from it.
    2. Ship rule-based detection before ML
      It's gradeable now, produces the labelled data an ML model needs later, and de-risks the AI phase if time runs short.
    3. Re-wire the frontend instead of rebuilding it
      The UI is already at production quality — replacing mockData.ts with real API calls is the fastest path to a genuinely working demo.
    4. Add the marketplace as the differentiator
      Plan comparison and sandboxed subscribe/cancel are fully achievable in-house and are exactly the kind of feature that reads as commercially credible to a panel.
    5. Rotate the committed secrets and fix native persistence
      Both are quick, both are the kind of thing a careful reviewer will notice immediately.
